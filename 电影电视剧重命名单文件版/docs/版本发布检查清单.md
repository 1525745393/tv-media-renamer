# 版本发布检查清单

> 流程已简化：**一条命令即可完成** 版本校验 → Changelog 升级 → 打 tag → 推送（触发自动发布）。
> 大版本（MINOR/MAJOR）建议先走预发布流程（见下文第六节）。

## 一、开发期（日常累积）

- [ ] 所有变更记录到 CHANGELOG.md 的 [Unreleased] 区块，按分类（新增/改进/废弃/移除/修复/安全）
- [ ] CI 保持绿色（push 后 GitHub Actions 自动跑 Lint/类型/测试）
- [ ] 应用内升级检测正常工作（启动日志出现「后台升级检测已启动」）

## 二、发布前准备

- [ ] 确认变更类型决定版本段位：
  - MAJOR（如 2.0.0）：不兼容的架构/行为变更
  - MINOR（如 1.4.0）：向后兼容的新功能
  - PATCH（如 1.3.1）：向后兼容的缺陷修复
- [ ] `core/version.py` 中 `__version__` 已更新（唯一版本来源）
- [ ] `RELEASE_DATE` 已更新为发布日期
- [ ] [Unreleased] 内容已整理为对用户可观察的描述

## 三、一键发布（自动化核心）

```bash
# 预览（推荐先看将执行的操作，不落盘）
python3 scripts/release.py

# 实际执行：自动验证 → Changelog 升级 → commit → tag → push → 触发自动发布
python3 scripts/release.py --execute
```

`scripts/release.py` 自动完成：

- [ ] **自动验证**：`check_release.py --release --check-git`（版本一致性 + Changelog 合法性 + 兼容性检查）＋ `--run-tests`（测试回归）
- [ ] **Changelog 升级**：[Unreleased] → `## [x.y.z] - 日期`，并在顶部重建空 [Unreleased]
- [ ] **提交 + 打 tag**（`v<版本>`）＋ **推送**（触发 GitHub Actions 自动构建发布）

## 四、自动验证内容（check_release.py 已覆盖）

- [ ] version.py 与 CHANGELOG 顶部版本一致（--release 严格模式）
- [ ] Changelog 分类合法（六类之一）
- [ ] **版本兼容性**：Python 版本在支持范围（3.9~3.13）、依赖清单可解析、主入口存在、关键模块可导入
- [ ] git 工作区无未提交改动（--check-git）
- [ ] 全功能测试通过（--run-tests，6/6）
- [ ] 性能基准测试通过（--benchmark，与 benchmark_results.json 对比）

## 五、发布后验证

- [ ] GitHub Actions Release workflow 全绿（验证 → Linux 构建 → Windows 构建 → 发布）
- [ ] Release 页面可见：
  - 双平台产物（Linux tar.gz / Windows zip）
  - SHA256SUMS.txt 校验文件
  - 自动生成的发布说明（CHANGELOG 提取 + 校验指引）
- [ ] 应用内升级检测指向新版本（可在本地运行旧版验证提示）

## 六、预发布流程（大版本推荐）

```bash
# 1) 创建预发布 tag（version.py 保持正式版本号）
git tag v1.4.0-rc.1 && git push origin tag v1.4.0-rc.1
# → 自动构建并创建 prerelease（不会推送给普通用户升级检测）

# 2) 测试通过后正式发布
python3 scripts/release.py --execute
```

## 发布后收尾

- [ ] CHANGELOG 顶部已有新 [Unreleased] 区块（release.py 自动创建）
- [ ] 如发现紧急问题：按 [发布回滚方案](发布回滚方案.md) 处置，或发布 PATCH 补丁版
